# Network Tunnel / Pivot Architecture

## Problem

The app runs on `192.168.8.10/24` but some authorized targets (e.g.
`172.16.159.5`) live on a segment only reachable through another host —
e.g. a second PC that's dual-homed onto both networks, or that has a VPN
client into the remote segment. The backend needs to reach those targets
without being on that segment itself.

## Core principle: a tunnel is a *route*, not a scope bypass

Everything in `05-SECURITY-ARCHITECTURE.md` still applies. A subnet
reachable only via a pivot is **not** automatically in scope just because
a tunnel to it exists — it must be added to `authorized_networks`
explicitly, the same as a directly-routable subnet, and it additionally
declares *which pivot* reaches it. No job is allowed to silently fall back
to "try direct, then try tunnel" — the route is resolved deterministically
from config, not guessed at connection time.

## Recommended mechanism: SSH local port forwarding, per job

This is the right default because it requires **zero changes to PRET
itself** — `conn.open()` already parses `host:port` and connects with a
plain `socket.connect()`. If the backend forwards a local port to the real
target over SSH and then hands PRET the string `127.0.0.1:<local_port>`
instead of the real target, PRET behaves exactly as it does today; it has
no idea a tunnel exists.

```
Backend (192.168.8.10)                    Pivot host (dual-homed)
   │                                            │
   │  ssh -L 127.0.0.1:<local_port>:            │
   │       172.16.159.5:9100 pivotuser@pivot ───┼──> 172.16.159.5:9100
   │                                            │
   ▼
PRET subprocess target = "127.0.0.1:<local_port>"
```

- Use `paramiko` (pure Python, cross-platform, no system `ssh` binary
  dependency — consistent with `04-DEPLOYMENT-PORTABILITY.md`'s "prefer
  cross-platform libraries" rule) to open the SSH session and request a
  `direct-tcpip` channel bound to a local port, rather than shelling out to
  the system `ssh` client.
- The forward is **job-scoped**: opened immediately before the adapter
  connects, closed immediately after the job finishes/times out/cancels —
  same lifecycle discipline as the per-job temp directories in
  `07-DATA-MODEL-AND-MEMORY.md` §5. Don't leave standing tunnels open
  between jobs; a forward that outlives its job is an unmonitored path
  into the remote segment.
- One forward per `(job, target:port)` — simple, auditable, and avoids
  needing a SOCKS-aware socket layer inside PRET's process.

## Advanced mechanism: SOCKS5 dynamic forwarding (only where needed)

Local forwarding needs to know the exact target in advance, which is fine
for assessment jobs (you already know the target) but doesn't help with
**discovery** across the tunnel. Two real limits to be explicit about:

1. **Broadcast/multicast discovery does not cross an SSH tunnel.** SNMP
   broadcast discovery and mDNS browsing rely on L2 broadcast/multicast —
   an SSH port forward is unicast TCP and simply doesn't carry them. If you
   need discovery on the remote segment, the pivot host itself has to run
   the discovery (a small agent, or the operator runs discovery locally on
   the pivot and adds results manually/via an import endpoint) — this is a
   real architectural limit, not a bug to work around in the tunnel layer.
2. For **unicast, targeted** operations where the exact target isn't known
   ahead of a scan (e.g. sweeping a /24 for open 9100/515/631), a SOCKS5
   proxy (`ssh -D` equivalent, via paramiko's `forward_tunnel`-style
   dynamic channel) is more practical than opening N local forwards. This
   requires making PRET's subprocess SOCKS-aware **without editing PRET's
   source**: launch it via a small wrapper script that calls
   `socks.set_default_proxy(...)` and `socks.wrapmodule(socket)` (the
   `PySocks` library) *before* importing/running `pret.py`'s `main()`, so
   every `socket.socket()` call PRET makes — unmodified — is transparently
   routed through the SOCKS proxy. Treat this as an **optional, later**
   capability (`09-ROADMAP.md` G.5 territory), not v1 — it adds a real
   dependency and a process-wrapping trick that's worth less scrutiny time
   than getting direct local-forwarding right first.

## Schema addition

Extends the schema you already deployed rather than replacing it:

```sql
-- migrations/002_add_network_routes.up.sql

CREATE TABLE public.network_routes (
    id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name text NOT NULL UNIQUE,
    route_type varchar(16) NOT NULL DEFAULT 'ssh_local_forward'
        CHECK (route_type IN ('direct', 'ssh_local_forward', 'ssh_socks')),
    pivot_host inet NOT NULL,
    pivot_port integer NOT NULL DEFAULT 22 CHECK (pivot_port BETWEEN 1 AND 65535),
    pivot_username text NOT NULL,
    credential_id bigint NOT NULL
        REFERENCES public.credentials(id) ON DELETE RESTRICT,
    is_enabled boolean NOT NULL DEFAULT true,
    created_at timestamptz NOT NULL DEFAULT now(),
    created_by_user_id bigint REFERENCES public.app_users(id) ON DELETE SET NULL
);

ALTER TABLE public.authorized_networks
    ADD COLUMN route_id bigint
        REFERENCES public.network_routes(id) ON DELETE RESTRICT;
-- route_id IS NULL  -> directly routable, no tunnel
-- route_id NOT NULL -> targets in this CIDR must go via that route

ALTER TABLE public.jobs
    ADD COLUMN route_id bigint
        REFERENCES public.network_routes(id) ON DELETE SET NULL;
-- recorded per-job for audit: which route (if any) this job actually used

CREATE INDEX authorized_networks_route_id_idx
    ON public.authorized_networks (route_id);
```

`credentials.kind` (from `07-DATA-MODEL-AND-MEMORY.md`) gets a new allowed
value, `ssh_key` or `ssh_password`, stored and decrypted under the exact
same rules as SNMP/HTTP credentials — never logged, never persisted
outside the encrypted blob, decrypted only for the duration of opening the
tunnel.

## Target-validation flow, updated

1. Resolve target IP (DNS-pin as already specified).
2. Look up which `authorized_networks` row (if any) contains it. If none
   → reject, same as today.
3. If that row's `route_id` is `NULL` → connect directly, exactly as
   before.
4. If `route_id` is set → look up the `network_routes` row, confirm
   `is_enabled`, decrypt its credential, open the forward (or confirm an
   existing one for this job can be reused — but still one forward per
   job, not a shared standing tunnel), hand the adapter
   `127.0.0.1:<local_port>` instead of the real target.
5. Record `jobs.route_id` either way, so the audit log always shows
   whether a job went direct or through a named pivot.
6. Tear down the forward when the job ends (success, failure, timeout, or
   cancellation all take the same cleanup path).

## Operational requirements on the pivot host

- A dedicated, least-privilege SSH account on the pivot PC, ideally
  restricted (via `authorized_keys` `command=`/`restrict` options or a
  scoped `ForceCommand`) to **port-forwarding only**, not an interactive
  shell — the pivot credential should not grant more than the tunnel
  itself needs.
- Key-based auth preferred over password auth for the pivot connection,
  stored via the same `credentials` encryption as everything else.
- The pivot host itself is in-scope for your own operational security
  review — it's now a trusted bridge between your assessment server and a
  second network, so treat its own hardening (patching, local firewall, who
  else has access to it) as part of this feature's threat model, not
  outside it.

## What NOT to do

- Don't let the browser specify an arbitrary SSH host/port/target to tunnel
  through on the fly — routes are admin-configured, named, and tied to
  specific authorized CIDRs, exactly like the operation catalog in
  `06-PROTOCOL-ADAPTER-DESIGN.md` is a fixed catalog rather than free text.
- Don't make tunnels long-lived/shared across arbitrary concurrent jobs
  without a clear reference-counted teardown rule — an orphaned forward is
  an unaudited path into the remote network.
- Don't reach for the SOCKS/dynamic-forwarding approach until targeted
  local forwarding is working and actually insufficient for a real use
  case — it's more moving parts (PySocks dependency, process-wrapper
  script, socket monkeypatching) for a capability (subnet sweeps across the
  tunnel) you may not need yet.
